# T4：資料庫 schema、Alembic、Repositories

- Phase：1
- 依賴：T3（compose、CI）
- 相關文件：`SPEC.md` §5.3、§11；`DECISIONS.md` D-005、D-013、D-014、D-015、D-018

## 背景 / 動機

Phase 1 要讓使用者建立並檢視 incident。這一步先把資料層建好：Alembic migration、三張核心資料表、RLS 全拒、async repositories，以及本機 compose 的一次性 migrate 服務。之後的 Phase 才在用到時加其他資料表（D-013）。

## 具體需求

### 1. 相依與 Alembic（`backend/`）

- 新增 runtime 相依：`alembic`。更新 `uv.lock`。
- `backend/alembic.ini`、`backend/alembic/env.py`、`backend/alembic/versions/`。
- `env.py` 從 `Settings.DATABASE_URL` 讀取連線，使用 psycopg 的**同步** engine 執行 migration（把 `postgresql+psycopg://` 直接用於 sync `create_engine` 即可）。不得把連線字串寫入 `alembic.ini`，也不得印到 log。
- `Dockerfile` 要把 `alembic.ini` 與 `alembic/` 複製進 runtime image，讓同一個 image 可執行 `alembic upgrade head`。
- Migration 必須可重入、失敗時整體 rollback（單一交易）。`downgrade` 也要實作並通過測試。

### 2. 初始 migration 內容

三張表（皆 UUID 主鍵，預設 `gen_random_uuid()`；時間欄位 `timestamptz`，預設 `now()`）：

**`profiles`**
- `id uuid pk`（對應 Supabase Auth user id，**不**自動產生，由 app 寫入）
- `email text null`
- `display_name text null`
- `role text not null default 'viewer'`，CHECK in (`viewer`,`operator`,`admin`)
- `created_at timestamptz not null`
- `email` 非 null 時須唯一（partial unique index，大小寫不敏感：`lower(email)`）

**`incidents`**
- `id uuid pk`
- `owner_id uuid not null` → FK `profiles.id`
- `scenario_key text not null`
- `title text not null`（長度 1–200，CHECK）
- `severity text null`，CHECK in (`P1`,`P2`,`P3`,`P4`) 或 null
- `status text not null default 'open'`，CHECK in SPEC §11.2 `incident.status` 全部值（`open | investigating | awaiting_approval | executing | verifying | resolved | mitigated | escalated | failed`）
- `affected_services text[] not null default '{}'`
- `is_public boolean not null default false`
- `created_at`、`updated_at`（`updated_at` 由 app 在更新時寫入）、`resolved_at null`、`deleted_at null`
- Index：`(owner_id, created_at desc)`、`(is_public, created_at desc) where deleted_at is null`

**`incident_events`**（append-only）
- `id uuid pk`
- `incident_id uuid not null` → FK `incidents.id`
- `event_type text not null`
- `agent_name text null`
- `summary text not null`
- `payload jsonb not null default '{}'`
- `created_at timestamptz not null`
- Index：`(incident_id, created_at, id)`
- 以 trigger 禁止 `UPDATE` 與 `DELETE`（raise exception）。`TRUNCATE` 不在範圍內。

使用 text + CHECK constraint 而非 PostgreSQL enum（理由見 D-014）。

### 3. RLS（D-005）

- 三張表皆 `ENABLE ROW LEVEL SECURITY`，不建立任何允許 policy。
- 若 `anon`、`authenticated` role 存在（以 `pg_roles` 判斷，用 `DO` block），則 `REVOKE ALL` 於這三張表。role 不存在（本機 pgvector image）時必須安全略過，不得失敗。

### 4. Models 與 Repositories

- `app/models/`：SQLAlchemy 2.0 typed declarative models（`Mapped[...]`），對應上述三張表；`app/models/base.py` 放 `Base`。
- `app/db.py` 新增：`async_sessionmaker` 工廠與 FastAPI dependency `get_session()`（每個 request 一個 session，成功 commit、例外 rollback、最後關閉）。保留現有 `check_database` 行為不變。
- `app/repositories/`：每個 repository 以 `AsyncSession` 初始化，只做資料存取，不含授權邏輯。
  - `ProfileRepository`：`get(id)`、`get_by_email(email)`、`create(id, email, display_name, role)`、`upsert_demo(...)`（供 T5 dev-login 使用：以固定 id 插入或更新 role）、`set_role(id, role)`。
  - `IncidentRepository`：`create(...)`、`get(id, include_deleted=False)`、`list(filters, limit, offset)`（filters：`owner_id`、`is_public`、`status`、`visible_to`——見下）、`count(...)`、`soft_delete(id)`、`set_public(id, is_public)`、`touch(id)`（更新 `updated_at`）。
  - `list` 的可見性以參數表達：`owner_id: UUID | None`、`include_public: bool`，條件為「`deleted_at is null` 且（`owner_id = :owner_id` 或（`include_public` 且 `is_public`））」，兩者皆為預設值時代表不限（供 admin）。排序 `created_at desc, id desc`。
  - `IncidentEventRepository`：`append(incident_id, event_type, summary, agent_name=None, payload=None)`、`list_for_incident(incident_id)`（`created_at asc, id asc`）。**沒有** update / delete 方法。
- Repository 一律使用參數化查詢（SQLAlchemy Core/ORM），不得字串串接 SQL。

### 5. Compose 與 CI

- `docker-compose.yml` 新增一次性 `migrate` 服務：使用 backend image，command `alembic upgrade head`，`depends_on: postgres: service_healthy`，`restart: "no"`。`backend` 服務加上 `depends_on: migrate: condition: service_completed_successfully`。
- `Makefile`：新增 `migrate`（`docker compose run --rm migrate`）。不要新增 `migrate-prod`（Phase 7）。
- CI（`.github/workflows/ci.yml`）`backend` job 加入 Postgres service container（`pgvector/pgvector:pg17`，含 health check），並設定 `TEST_DATABASE_URL` 與 `CI=true`。
- `.env.example` 加入 `TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/postgres`（註解說明這是測試用管理連線，測試會自行建立與刪除暫時資料庫）。

### 6. 測試

- 測試 fixture（`tests/conftest.py` 或 `tests/db/conftest.py`）：以 `TEST_DATABASE_URL` 連到管理資料庫，建立一個隨機名稱的暫時資料庫，對其執行 `alembic upgrade head`，測試結束後 drop。每個測試在 transaction 中執行並 rollback，或每個測試前清空資料表，以確保隔離。
- 若 `TEST_DATABASE_URL` 未設定：在本機（`CI` 未設定）時 DB 測試以明確訊息 skip；在 CI（`CI=true`）時必須讓測試**失敗**而不是 skip。
- 至少涵蓋：
  - migration `upgrade head` → `downgrade base` → 再 `upgrade head` 成功。
  - CHECK constraint（非法 role / status / severity / 過長 title）被資料庫拒絕。
  - `incident_events` 的 UPDATE / DELETE 被 trigger 拒絕。
  - 三張表 `relrowsecurity = true`；當手動建立 `anon`/`authenticated` role 後重跑 revoke 邏輯，這些 role 對三張表無任何權限（測試內建立並清除 role）。
  - 各 repository 方法的行為，特別是 `IncidentRepository.list` 的可見性條件組合（owner only、owner + public、admin 全部、soft-deleted 不出現）與分頁排序。
  - `ProfileRepository.upsert_demo` 重複呼叫為冪等。
- 既有 49 個測試維持通過；整體 coverage ≥ 80%；repositories 與 models 的 coverage ≥ 90%。

## 驗收標準

1. 在 `backend/` 下 `ruff check`、`ruff format --check`、`mypy`、`pytest --cov` 全數通過（以本機 compose 的 postgres 作為 `TEST_DATABASE_URL`）。
2. 全新環境 `docker compose up --build`：`migrate` 服務成功結束（exit 0），`backend` 隨後啟動，`/health/ready` 回 200；再次 `up` 時 `migrate` 仍成功（冪等）。
3. 以 `psql` 檢視：三張表存在、RLS 已啟用、`incident_events` 無法 UPDATE / DELETE。（回報中附上實際指令與輸出摘要。）
4. CI 的 `backend` job 在有 Postgres service 的情況下通過，且 DB 測試確實執行（未被 skip）。
5. `docker build ./backend` 成功，image 內可執行 `alembic upgrade head`。

## 明確排除的範圍

- 不建立 `agent_runs`、`tool_executions`、`approval_requests`、runbook、評測等其他資料表（D-013）。
- 不做 pgvector extension 或 vector 欄位（Phase 4）。
- 不做 JWT / 授權 / API endpoint（T5、T6）。
- 不做 scenario registry（T5）。
- 不做 seed script、`migrate-prod`、Supabase 專案連線。
- 不修改既有 health endpoints 的行為。
